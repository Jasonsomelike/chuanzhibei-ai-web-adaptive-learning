## 一、这个版本做了什么

预指导的作用是在省赛截止前拿到评委意见，所以这一版的目标不是「功能多」，而是**把核心主张做成可验证的东西**，让评委能判断技术方案是否成立。

已完成并经过验证的部分：

| 模块 | 具体内容 | 怎么验证 |
| --- | --- | --- |
| 知识图谱 | 《数据结构》40 个知识点、60 条先修边，覆盖 8 章 | `npm run kg:validate` 检查无环、无悬空引用 |
| 题库 | 120 道单选题（每知识点 3 题），每题带难度与解析 | 同上，含难度分布校验 |
| 掌握度模型 | 难度加权 Beta-Bernoulli 后验，输出点估计与不确定度 | 12 条单元测试 |
| 路径规划 | 纯函数：先修闭包 → 深度+ZPD 排序 → 预算装包 | 24 条测试，含「同输入两次结果完全一致」 |
| 诊断流程 | 按先修顺序出题，答完即时更新掌握度并显示变化 | E2E 实测：答 3 题后路径变化 |
| 路径页 | 反事实对比（改预算看差异）+ 手动改写（拖动/删除，实时标出违规） | E2E 实测：改预算后路径重算 |
| 导师对话 | BM25 检索 + 强制引用知识点；无 API key 时退化为结构化拼装 | E2E 实测：回答含 [cXX] 引用 |
| MCP 端点 | tools 4 个 / resources 2 个 / prompts 2 个 | 13 项 JSON-RPC 协议测试全过 |
| 密钥扫描 | 提交前自动扫描，已用植入密钥验证它能抓到 | `npm run check:secrets` |

## 二、技术方案的一句话说明

**大模型不参与路径排序，只做解释。**

这是整个方案的核心取舍。自适应学习产品最容易走的路是「让 LLM 读学生数据然后推荐下一步」，但这样做有两个问题：一是路径无法复现（同一学生同一状态，两次推荐可能不同），二是无法解释（学生问「为什么排这一步」，只能得到模型的自我叙述）。

我们改成：排序由纯函数完成，输入是掌握度快照 + 先修图 + 时间预算，输出是确定的路径；LLM 只负责把「为什么这样排」讲成人话，并且必须引用具体知识点与数值。

这样做的好处是三个可验证的承诺：

1. **路径可复现**——`path_hash` 对输出取 SHA-256，同一输入 + 同一版本得到同一指纹。改算法或图谱，指纹立刻变，CI 会红。
2. **理由可追溯**——每一步都带数值理由（「已掌握 68%（±19），距目标还差 −8 个百分点」），不是套话。
3. **大模型可缺席**——拔掉 API key，路径完全一样，导师回答退化为检索拼装但仍可用。

## 三、请评委重点看的三处

### 1. 路径页的可复现性面板

地址：`/path`，页面底部「可复现性」区块。

这里显示当前路径的 SHA-256 指纹、算法版本、图谱版本。指纹不含任何模型标识——换大模型不会改变指纹，因为排序根本不用大模型。

**验证方法**：记住指纹，刷新页面，指纹不变；把预算从 90 分改成 120 分，指纹变化。

### 2. 路径页的反事实对比

地址：`/path`，「反事实：如果时间不一样」区块。

选一个对照预算，页面会标出哪些步骤在对照预算下会被推迟。这是「交互模式创新」的具体落点——不是加个动画，而是让学生能问「如果我今天只有 30 分钟会怎样」并立刻看到答案。

### 3. 导师页的模式标注

地址：`/tutor`，页面顶部。

当前显示「知识库检索」模式（未配置 API key）。这不是故障，是本项目的设计选择。每条回答下方列出引用的知识点 id，引用来自检索结果而非模型自述。

**如果评委想验证大模型模式**：在 `.env.local` 里填入 `DEEPSEEK_API_KEY` 后重启，模式会变成「大模型 + 检索」，引用列表不变。

## 四、明确没做的部分

预指导的价值一半在于拿到批评，所以这里如实列出缺口，不粉饰：

| 缺口 | 影响 | 计划 |
| --- | --- | --- |
| **教师班级视图未实现** | 「社会价值」与「场景真实性」两个评分点的支撑不足 | W3（11/04–11/10） |
| **题库与图谱未经任课教师签字** | 内容正确性未经教学现场验证 | 已联系任课教师，待逐条核对 |
| **无真实学生使用数据** | 无法给出「使用后成绩提升」的证据 | 计划 W3 前测、W4 后测 |
| **路径页是列表，不是图形画布** | 视觉冲击力弱于设计稿 | 因首屏预算推迟（elkjs 单独 gzip 464KB） |
| **未做性能实测** | 无法证明 Lighthouse ≥90 | W4 统一测 |
| **多模态只做了题目文本** | 「多模态能力 5%」拿不到高分 | 计划接 OCR（拍照转题目），优先级低于教师视图 |
| **无演示视频与技术文档** | 省赛硬性要求 | W4 产出 |

## 五、怎么跑起来

```bash
npm install
npm run dev          # http://localhost:3000
```

不需要配置任何环境变量。想跑完整验证：

```bash
npm run verify        # 类型检查 + 94 条单元测试 + 数据集校验
npm run check:secrets # 密钥扫描
```

端到端测试（需先 `npm run build && npm start`）：

```bash
BASE_URL=http://127.0.0.1:3000 npx tsx scripts/smoke.ts
BASE_URL=http://127.0.0.1:3000 npx tsx scripts/mcp-smoke.ts
```

## 六、希望得到的反馈

1. **技术方案层面**：「大模型不参与排序」这个取舍是否成立？在评分表「AI 技术深度 35%」下，会不会因为 LLM 用得「不够重」而失分？我们的判断是 Agent 编排（导师的检索-回答链路）与 MCP 集成足以支撑，但想听评委意见。
2. **内容层面**：40 个知识点、60 条先修边的划分是否合理？有没有明显该连没连的边？
3. **评分策略层面**：教师班级视图与多模态 OCR，在剩余 3 周里哪个优先级更高？
4. **呈现层面**：路径用列表还是必须做成图形画布？如果图形化对「用户体验」维度影响显著，我们会调整排期。
